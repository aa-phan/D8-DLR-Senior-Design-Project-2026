<objective>
Lead Phase 3 with the measurement path the whole phase stands on: the backfill writes a per-step
trace of what the live per-city pipeline actually did, and an offline analysis module turns that
trace (plus the archive) into the VAL-01 tables.

Purpose: VAL-01 needs, per city and per step, the computed rating, the reported rating, which gate
fell back, the inputs and their providers. The backfill log only keeps the reported rating and gate
names, and the archive stores the static rating on fallback rows, so neither can say how often a
fallback reported MORE than physics computed (the Austin G4 case in STATE.md "Output
Observations"). The trace keeps exactly what run_city_pipeline returned, so the analysis measures
the live path rather than a reconstruction of it. Plans 03-02 (the owner's real run), 03-03
(VAL-02) and 03-04 (the report) all consume this trace format and CLI.

Output: `--trace-path` on `backend/backfill_archive.py`; `backend/real_data_validation.py` with the
`completeness`, `manifest` and `report` (VAL-01) subcommands; two offline test files.
</objective>
