<objective>
Unify the safety monitor with the real IEEE 738 thermal model so the fail-safe gate chain judges the
same number the physics core would compute, and make every gate resolve toward the static rating
rather than toward an optimistic guess.

Purpose: ROADMAP Phase 3 Success Criteria 1 and 2. Today `DLRSafetyMonitor._compute_ampacity` uses a
placeholder linear expression that disagrees with `thermal_model.ieee738_ampacity`, so DS-F7's gating
is applied to a fictional value and DS-NF5's fail-safe promise is only structurally, not actually,
kept. This plan makes the gated number real, recalibrates the plausibility gate that would otherwise
reject 3 of the 4 D-00 cities outright, and closes the G1/G2 stale-value and G5 no-fallback holes.

Output: a per-location-constructible `DLRSafetyMonitor` whose every reported rating is either a real
IEEE 738 value or that location's static rating, plus a green test suite that proves the equivalence.
</objective>

<assumption_delta_decision>
**Noun now primary:** the **corridor** — a `line_azimuth`-bearing path between two city endpoints,
discretized into multiple weather-sampling points. This generalizes the prior implicit
single-station-per-city model.

**Decision:** `promote`. The corridor/multi-point model becomes the primary geographic noun across
station discovery, static ratings, and corridor discretization. A single-station lookup is now one
instance of the general per-point weather lookup (the D-08 candidate-probe path), not a separate code
path.

**Rationale:** CONTEXT.md D-00 through D-09 already made this decision during discuss-phase. This
block records it; it does not re-decide it. Concretely for this plan: `DLRSafetyMonitor` stops being
a single global instance with one global `ConductorConfig` and one global `RATING_BOUNDS`, and becomes
a per-location object constructed from `config.py` — which is exactly the shape Plan 03-02's corridor
code needs when it builds one monitor per corridor.
</assumption_delta_decision>

This is the one item in Phase 3 where the source artifacts state a requirement the current code does

ROADMAP Phase 3 Success Criterion 2 and REQUIREMENTS.md DS-NF5 both list "large rating swing" in the
same clause as the other four fallback triggers: "causes the reported rating to fall back toward the
static rating, never toward an optimistic guess". Today G5 does not fall back at all. It appends an

How often the system then sits in fallback depends entirely on the threshold, which is currently a
flat 150 A class constant calibrated against the placeholder formula's output range. Under real
IEEE 738 values (roughly 1700-2300 A for ordinary Texas summer conditions) a flat 150 A threshold is
6-10 percent of the rating and would trip on routine diurnal variation.

  </context>

  <options>
    <option id="option-a">
      <name>Conservative fallback with a relative threshold (recommended)</name>
      <pros>

existing fixture's static_rating of 1000 yields exactly 150.0 A, preserving the current constant's
meaning while scaling correctly across the four cities (1450-3000 A). On a large swing the reported
rating is the smaller of the computed rating and the static rating, which is conservative in both
directions: an upward swing is capped at the static rating, and a downward swing keeps the lower
computed value rather than being lifted to a higher static rating. last_good_rating is still updated

genuine sustained weather change resolves in one cycle. Satisfies Success Criterion 2 literally.

      </cons>
