Close WX-05: prove that a station-based row and a grid-based row genuinely combine into one row per
timestamp against `PIPELINE_SCHEMA`, with each field's provenance naming the provider that actually
supplied it — before any real second provider exists to discover the design was wrong.

grid provider. Phase 7's real Open-Meteo/ASOS work then plugs into a seam that is already tested,
rather than a seam that is being invented under integration pressure.

Output: `attach_city` and `merge_observations` in `weather_provider.py`; a test-only mock grid
provider and a full merge test group; the C4 spec brought current; the ECE 464 acknowledgement entry

Add `MERGE_KEY: tuple[str, str]` holding the literal `("city", "datetime_utc")`, with a short comment
recording that D-05 chose city over station ID and raw coordinates because every request in this
codebase already resolves to one of the four `config.CITY_COORDINATES` entries.

Define `attach_city(frame, *, lat=None, lon=None) -> pd.DataFrame`. Return `frame` unchanged when it
is `None` or empty. Otherwise `frame.copy()` first — mirroring `station_explorer.nearest_stations`'s
copy-before-annotate convention and `attach_provenance`'s own no-mutation contract — then set a `city`
column. When `lat` and `lon` are supplied (the grid-request case, where the coordinates came from the
caller rather than from the data) set every row's `city` to `resolve_station_city(lat, lon)`. When
they are not supplied, derive per row from the frame's own `lat`/`lon` columns via
`resolve_station_city`, yielding `None` for any row whose coordinates do not resolve. Raise
`ValueError` if the frame is non-empty, `lat`/`lon` were not supplied, and the frame has no `lat`
column — a caller asking for city attribution on a frame with nothing to attribute from is a bug, not
a null case.

Define `merge_observations(station_frame, grid_frame) -> pd.DataFrame`. Return the other side
(re-indexed and sorted) when one side is `None` or empty; return an empty `pd.DataFrame()` when both
are. For each non-empty side, require both members of `MERGE_KEY` to be present as columns or index
levels and raise `ValueError` naming the missing one otherwise. Count rows whose `city` is null and,
if any, raise `ValueError` stating that count and that unresolvable rows cannot be merged — do not
proceed with a null key, because pandas will happily group every unresolvable row from both providers
under one shared key and emit a single row stitched together from unrelated stations, which is a
fabricated observation wearing a real provenance label. Then `set_index(list(MERGE_KEY))` on both
sides and return `station_frame.combine_first(grid_frame).sort_index()`.

`combine_first` is the right primitive rather than an outer `merge` plus per-column `fillna`: it fills
nulls column-by-column from the other frame and unions both indexes, which is exactly D-05's
semantics, and the calling frame's non-null value winning is exactly `data_provider.md`'s composition
— station-based wind/temp primary, grid-based solar filling what stations lack. Put the station frame
on the left for that reason.

The honesty of the merged provenance rests entirely on an invariant `attach_provenance` already
establishes: a provenance cell is non-null exactly when its mapped data cell is non-null. Because
`combine_first` fills each column independently, that pairing is preserved automatically — the grid
frame's `solar_source` arrives with its `solar_radiation`, and the station frame's null
`solar_source` does not block it. Do not add any post-merge provenance rewriting, defaulting, or
backfill step: doing so would re-introduce exactly the false-provenance risk the column-wise fill
avoids.

Do not wire `merge_observations` into `fetch_weather`'s dispatch. No real grid provider exists until
Phase 7, and `_fetch_grid`'s explicit `ValueError` is the correct behaviour until one does. This
function is the tested seam Phase 7 plugs into.
