<objective>
Build `backend/pandapower_job/engine.py`, the entry point a pandapower run uses (the Phase 5 workflow will call it). It loads the mapping once, refuses settings pandapower cannot reproduce at stage `mapping` (ENG-02, D-07), runs the unchanged study through `study.make_study(..., solver="pandapower")`, and stores the solve and scaling settings with each run (ENG-05). Before PSE-02 those settings are clearly named placeholders (D-06); afterwards the recorded values drop in through a fail-closed loader. Its first task is the in-memory tier of ENG-06: a full four-city study on the case39 fixture with the placeholder mapping, no live data, validated by the existing `run_record` code.

Purpose: the API gives correct numbers. The engine makes sure a run cannot silently use a mode pandapower does not honour, cannot pass placeholders off as PSS/E's settings, and cannot be stored as a PSS/E result.
Output: `engine.py`, `pandapower_engine_test.py`, and the owner-local `pandapower_engine_recorded_test.py`.

**Assumptions for the owner (RESEARCH open questions 1, 4 and 6; reversible; confirmed at plan 02-07's checkpoint):**
- Q1: a backend whose `enforce_q_lims` is None (PSE-02's reactive-limit classification was inconclusive) is refused at stage `mapping`. The engine never picks a value (D-14: copy what PSS/E reports).
- Q4: `voltage.source "case"` is refused, because the builder does not carry PSS/E's emergency voltage limits. Extending the builder would change Phase 1 code.
- Q6: "stored with each run" means a `solve_settings` record in every dispatch row's `details` (free JSON, no schema change; Phase 3 owns the schema). A run-level column would be Phase 3's migration.
- A3: the real private mapping uses the defaults (`thermal.basis "current"`, `voltage.source "config"`, `solve.options null`). If not, the preflight refuses it on first use, loudly.
</objective>
