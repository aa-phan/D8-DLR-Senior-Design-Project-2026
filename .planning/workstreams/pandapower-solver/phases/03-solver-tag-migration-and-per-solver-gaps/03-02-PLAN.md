<objective>
Carry the solver tag through the stdlib PSS/E job package (DB-02, D-04): a registry of solver tags and run-id prefixes in `contract.py` that a solver package fills on import, a `solver` field on the run context and the study results, a `solver="psse"` keyword on `run_once`, a run record that gains `solver` and `solver_version` only for a non-PSS/E run, and a writer that refuses a mismatched tag before it executes anything and writes a tagged run with a second, 19-column INSERT.

Purpose: success criterion 2 of Phase 3. A pandapower run must never be stored as `psse`, and the unchanged PSS/E job must keep writing with exactly `contract.INSERT_RUN_SQL`, so it still works on a database where the migration has not been applied yet (the laptop job is paused, not retired).
Output: the edited `contract.py`, `run_record.py`, `job.py`, `writer.py`, and `backend/tests/psse_solver_tag_test.py`. No database, no pandapower: this plan runs completely on this machine.

Why a registry and not the name: `backend/tests/pandapower_import_gate_test.py` fails if any `psse_job/*.py` file contains the second solver's name in any letter case, comments and docstrings included, so `psse_job` refers to it only as "the second solver" (or "another solver") and the solver package registers its tag (plan 03-04), the same shape Phase 2 used for `study.register_solver`. `constants.py` is deliberately not edited: its vocabularies are tested against the frozen reference DDL's CHECK lists, which has no solver column.
</objective>
