<objective>
Ship the DBX-02 proof as code: one function the laptop (or the owner) runs against the live credential to show that the job's database role can write the four PSS/E result tables and cannot touch the ratings, and that the publishable key can read ratings and cannot change them. The Mac proves the checks against a local Postgres that carries the reference DDL and against a loopback PostgREST stand-in, including that each check goes red when its privilege is planted; the live run waits for Phase 6 (plan 03-08).

Purpose: DBX-02 says the job reads ratings only through Phase 6's access, writes only to the PSS/E result tables, and cannot change `city_rating`. There are two credentials, not one: the REST publishable key reads, and the `dlr_psse_writer` role writes. The writer role holds INSERT and SELECT on the four tables and nothing on `city_rating`, `pipeline_run` or `latest_rating`; so "cannot change city_rating" must be shown for both. Phase 1 proved the role's privileges on a throwaway database (`backend/tests/psse_schema_pg_test.py`); this plan turns that proof into a shipped, safe-by-construction command that runs against the live credential.
Output: `backend/psse_job/credcheck.py` and `backend/tests/psse_credcheck_test.py`.

Honest scope: on local Postgres 18.6 the role is the one Phase 1's DDL creates, and PostgREST is a loopback stand-in. This plan does not prove that Phase 6's live migration applied the same grants, that Supabase's session pooler accepts the custom role, that role memberships and function privileges on the live project are clean (live Supabase has objects the local database lacks), or that the live publishable key answers 401 or 403 and the live view is readable. Each is runbook step 8 (plan 03-08) and is labelled UNVERIFIED until then. A where-false statement raising 42501 is verified here for PostgreSQL 18.6 only.

Questions carried forward: (1) Does the shared session pooler accept the custom role through the form `ROLE.PROJECT-REF` without any Supabase-side setting beyond the migration (research open question 6)? Plan 03-08 asks the owner. (2) May `--write-proof` run on the live database at all, given that a rolled-back insert still leaves dead tuples? The proof is opt-in and the owner decides in plan 03-08; the one real write there proves the same insert path.

## Design decisions (planner-locked)

| ID | Decision |
|----|----------|
| D-01 | The privilege checks are derived from the catalog, not from a hard-coded list of forbidden tables: every relation of kind table, partitioned table, view, materialized view or foreign table in schema public except the four result tables is tested for each of SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER (and MAINTAIN when the server is 17 or newer), through `has_table_privilege(current_user, oid, privilege)`, which also sees grants to PUBLIC and through role membership. A relation that does not exist locally (`latest_rating` before Phase 6) simply is not listed, so the check never errors on it. |
| D-02 | The active statements are where-false statements (verified during planning on a throwaway PostgreSQL 18.6: as the writer role each of update, delete, insert-select and select on city_rating, select on pipeline_run, update and delete on psse_run raised 42501 even with `where false`, because permissions are checked when the statement starts). Each runs inside `conn.transaction(force_rollback=True)`. Only SQLSTATE 42501 is a refusal; any other error (for example a missing relation) is FAIL as inconclusive, and success is FAIL "the statement was allowed". |
| D-03 | The REST write attempts are PATCH and DELETE on `/rest/v1/city_rating?city=eq.__no_such_city__` with the publishable key in the apikey header only and a body of one field, so even a wrongly permissive key changes no row. They are sent only after the ratings read (which applies the job's own guards: https or loopback, no secret or service_role key) returned 200. 401 and 403 pass; 2xx fails; anything else fails as inconclusive. |
| D-04 | The write proof is opt-in (`write_proof=True`): a synthetic complete fallback run is built from the job's own functions (ratings.select_ratings with a fetch returning no rows, so every city is static and missing; dispatch.build_dispatch_row for the dispatch rows; run_record.build_run_record, result_rows and validate_results), written with writer.write_run inside `conn.transaction(force_rollback=True)`, counted inside the block and counted again outside it. The run's case label is `credcheck-synthetic` and its job_version `credcheck`. |
| D-05 | Exit codes (equal to the launcher's table, plan 03-01 D-03; plan 03-06 tests the equality): 0 every check passed, 6 any FAIL, any unmet REST configuration (unless skip_rest) or a connection that could not be made. SKIP rows exist only for the REST write attempts that were not sent after a failed read, or for the whole REST leg when skip_rest is set. |
| D-06 | The report never prints a URL, user, host or key: details hold relation names, privilege names, SQLSTATE codes, HTTP status numbers and counts. Relation names are the project's own table names, already public in the migrations. |
