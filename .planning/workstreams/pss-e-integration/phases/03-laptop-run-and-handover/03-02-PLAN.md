<objective>
Make a missing hour visible (SCH-02): one SQL statement over `public.psse_run.slot_time` that lists the hours with no complete result set, a small Python wrapper the laptop (or anyone holding the writer credential) runs, and tests that hold the statement to an independent reference on local Postgres.

Purpose: Phase 1 decided that a run which dies mid-way leaves a gap, not a row (D-04), and that the laptop being off or asleep is expected (REQUIREMENTS "Always-on hourly guarantee" is out of scope). SCH-02 asks that such an hour be visible through a stated query or check. The statement below is that query; the wrapper is that check. Because the slot is the UTC hour floor of the laptop's start time, the check needs no new column and no DDL change.
Output: `docs/data-science/schema/psse_run_gaps.sql`, `backend/psse_job/gaps.py`, `backend/tests/psse_gaps_pg_test.py`.

Honest scope: the Mac proves the statement's logic and the wrapper on local Postgres 18.6. It does not prove that the live table shows the real laptop's hours, that the laptop clock agrees with the database (a clock more than a few minutes off moves a run into the wrong slot and makes a false gap and a doubled slot; the guide tells the installer to check `w32tm`), or daylight-saving effects (the statement works in UTC only). Those are runbook step 10 (plan 03-08, an induced gap and a next-day check).

Questions carried forward: (1) Is "failed_only" (the job ran but every run failed) worth listing as a gap to the owner, or only the strict no-run hours? This plan lists both and labels them, because "no results this hour" should never be hidden; the owner may filter. (2) Should the gap check ever run unattended (for example a daily task with `--fail-on-gaps`)? Not in this milestone's scope; the exit code 5 exists so a later monitor can use it.
</objective>

## Design decisions (planner-locked)

| ID | Decision |
|----|----------|
| D-01 | Gap logic lives only in the SQL file. It was run against a throwaway local Postgres 18.6 during planning (empty table: zero rows; a seeded set with a duplicate slot, a failed-only slot, a failed plus complete slot and a current-hour run gave exactly the expected rows), so the file starts from tested text; the plan's tests still gate it. |
| D-02 | Rows: slot_time (timestamptz, UTC), gap_kind (`no_run` or `failed_only`), runs (rows in the slot), failed_runs. A slot with at least one ok or fallback row is never listed. |
| D-03 | The gap check uses the same credential as the job (dlr_psse_writer holds SELECT on psse_run and a select policy), on a read-only session (`conn.read_only = True`), so it cannot change anything even if the file were edited carelessly. |
| D-04 | The wrapper reads two things: the gap statement and one summary statement (`select count(*), min(slot_time), max(slot_time) from public.psse_run`) for the header and for "no runs recorded". The summary is not gap logic. |
| D-05 | Exit codes (equal to the launcher's table, plan 03-01 D-03; plan 03-06 tests the equality): 0 ok, 5 gaps found with fail_on_gaps (also "no runs recorded"), 6 the check could not run. |
| D-06 | The statement uses `now()` so it runs unchanged in the Supabase SQL editor. Tests that need a fixed clock seed rows relative to the database's own current UTC hour and retry once if the hour rolls during the run. |
