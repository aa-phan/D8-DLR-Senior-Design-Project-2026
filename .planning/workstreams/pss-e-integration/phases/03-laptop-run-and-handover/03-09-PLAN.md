<objective>
Close the gap that stopped laptop session A at runbook step 2. On the licensed laptop (PSS/E 36.4, Python 3.14.0 64-bit, Windows 10) `psse_run_hourly.py selftest` stops with `PSS/E could not be started: PsseUnavailable: psspy could not be imported (ImportError)`. By-hand experiments in the 03-07 record ("Finding from step 2") show that importing `psspy` directly fails with `DLL load failed while importing psscommon` even with the PSSPY314 and PSSBIN folders on `sys.path` and registered with `os.add_dll_directory`, and that appending the PSSPY314 folder, importing PSS/E's own helper module `psse3604` and then importing `psspy` works. The helper's header says it sets the PSS/E 36.4.x environment so PSS/E can run outside its own interface from any interpreter, and it delegates to `psseloc`. So the launcher must import that helper before `psspy`, and the helper's name follows the PSS/E version, so it must come from configuration.

Purpose: nothing about real PSS/E can be proved (plan 03-07 steps 2 to 6, plan 03-08) until real `psspy` starts under the launcher. This plan makes it start on the laptop's PSS/E 36.4 and keeps every existing Mac proof (tests and fakes) unchanged when the new key is unset. It adds no other behaviour.

## Design decisions (planner-locked from the brief and the 03-07 evidence)

| ID | Decision |
|----|----------|
| D-01 | The key is `PSSE_ENV_MODULE`, kind `module`, not secret, required for no mode, no default; unset means today's behaviour (psspy imported directly), which keeps every existing test and fake green. It sits right after `PSSE_PSSPY_DIR` in `CONFIG_KEYS` and in the guide's table, because it describes that folder's contents. The name copies the helper's own wording ("set PSSE 36.4.x Environment"). Rejected: a hard-coded `psse3604` (the name follows the PSS/E version and would break the fakes and any other install), deriving the name from the psspy folder name (`PSSPY314` does not hold the minor version), and scanning the folder for a `psse*` module (it would import code nobody named). |
| D-02 | Validation: a plain Python module name is ASCII letters, digits and underscore, first character not a digit, 1 to 64 characters, matched with `\Z` (never `$`, which accepts a trailing newline). No dot (so no package path, and `psse3604.py` is refused), no slash, no space, nothing non-ASCII. Checked twice: at configuration reading, as `key PSSE_ENV_MODULE: must be a plain Python module name such as psse3604 (letters, digits and underscores, not starting with a digit; no dots, slashes, spaces or .py)` (exit 2, naming the key and never the value; the reader runs before the lock, before `add_search_dirs` and before any loader call), and again in `load_psspy` (`PsseUnavailable`) for any caller that does not go through `read_config`. The public function is `launcher.is_plain_module_name(value) -> bool` (False for anything that is not a `str`). |
| D-03 | The import is inline in `load_psspy`, the only function of the repository that imports `psspy` or a module chosen by configuration: `importlib.import_module(name)` after `launcher.main` has appended the search folders (`add_search_dirs`, unchanged) and before `import psspy`, with the name taken from the configuration (a variable, never a literal). `psse_run_hourly.py` gains `import importlib` at module level, which imports nothing by itself. Never at module import time. |
| D-04 | Messages, class only, never text: helper failing with ANY exception (the helper runs PSS/E code) is `PsseUnavailable("the module named by PSSE_ENV_MODULE could not be imported (ClassName)")`; a name failing the re-check is `PsseUnavailable("PSSE_ENV_MODULE is not a plain module name")`; psspy failing keeps `psspy could not be imported (ClassName)` and, only when the key is unset, ends with `; PSSE_ENV_MODULE is not set` as the pointer for the next person. The key is named, its value never printed. |
| D-05 | Unchanged: `add_search_dirs`, the DLL folder registration, `start_psspy`, every selftest and probe output line and count (no new printed line). Only their comments change: the session-A observation that the DLL folder alone was not enough on 36.4 is recorded where the code says "needed or enough". |
| D-06 | The fake: a folder whose `psspy.py` raises `ImportError` with the laptop's text (`DLL load failed while importing psscommon: The specified module could not be found.`) unless the environment variable `FAKE_PSSE_ENV_READY` equals `1`, and otherwise logs `psspy`; its helper module sets that variable and logs `helper`, both into one import log that the parent test reads. Entry-script proofs run in `-I` subprocesses (no state leaks); in-process proofs set the variable with `monkeypatch.setenv` first (teardown removes it), copy `sys.path` and clear `psspy` and the helper from `sys.modules` before and after. |
| D-07 | Documents: add the key to the guide's table (same position as the code), example and a short paragraph; add a prerequisites row and the troubleshooting rows; the runbook's step 0 row and "Should show" sentence, step 1 block, step 2 text and steps-table cell; the register rows U01 (corrected), U07 (observation added), U33 and U34 (new). The interpreter and psycopg decision table, the hand-over record and the status lines are left to plan 03-07 task 6. |
| D-08 | The resume point above is part of the deliverable: the plan, its SUMMARY and the runbook's step 2 text say what the user does on the laptop. |
