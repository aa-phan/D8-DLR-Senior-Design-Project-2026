<objective>
Give the person installing the job a Task Scheduler definition they can trust (SCH-01): a committed XML template with deliberate settings and placeholders only, a renderer that fills it safely, and tests that hold the template to its stated policy.

Purpose: Task Scheduler's defaults are wrong for a laptop (battery start and stop on, no wake, no catch-up control), and a hand-edited XML is where quoting, encoding and secrets go wrong. The template pins the settings the research justified: `IgnoreNew` so a still-running hour is never overlapped, a 45 minute limit, battery flags off, `StartWhenAvailable` off so a missed hour stays a visible gap instead of a burst after wake, `WakeToRun` on, and an interactive token so no password, administrator right or batch-logon right is needed. The renderer removes the edit-by-hand step and its typical mistakes; the lock from plan 03-01 is the second line against overlap.
Output: `docs/data-science/ops/psse_hourly_task.xml`, `backend/psse_job/taskxml.py`, `backend/psse_render_task.py`, `backend/tests/psse_task_xml_test.py`.

Honest scope: everything here is checked as text and against the launcher's parser. Nothing was registered with Windows Task Scheduler on any machine, and Microsoft's schema was not run against the file. Every behaviour of the real scheduler (accepting the file, repeating indefinitely, wake, battery, exit-code pass-through, registration by a standard user) is UNVERIFIED until the laptop session (plan 03-07, runbook step 6).

Questions carried forward: (1) Which minute past the hour should the job start? Default 15: the live pipeline writes the hour's rating row a few minutes after the hour, and a start after about HH:30 can find the previous row older than 90 minutes and go all-static with reason stale (spec note for Phase 3), so :15 leaves the rating fresh and ends a 25 minute study before :45. (2) Is `StartWhenAvailable` false acceptable (a missed hour stays a gap) or does the owner prefer one catch-up run after wake? The template says false; the guide (plan 03-06) states the trade-off. (3) Can the teammate register a task for their own account without administrator rights, or must someone else do it from their session (research assumption A8)? Plan 03-07 asks.
</objective>

## Design decisions (planner-locked; the research's template except where a reason is given)

| ID | Decision |
|----|----------|
| D-01 | Template placeholders: PYTHON_EXE (the interpreter that matches PSS/E's psspy folder), ARGUMENTS (built in code, never typed), WORK_DIR (a folder only the user can write, not Downloads), START_BOUNDARY (local time, YYYY-MM-DDTHH:MM:SS). The research had separate entry and config placeholders; one ARGUMENTS placeholder built by `taskxml.build_arguments` avoids a hand-quoted string. |
| D-02 | Settings, each pinned by a test: one TimeTrigger, Enabled true, Repetition with Interval PT1H and no Duration and no StopAtDurationEnd; Principal LogonType InteractiveToken, RunLevel LeastPrivilege, no UserId and no password element; MultipleInstancesPolicy IgnoreNew; DisallowStartIfOnBatteries false; StopIfGoingOnBatteries false; AllowHardTerminate true; StartWhenAvailable false; RunOnlyIfNetworkAvailable false (the launcher's preflight handles the network); WakeToRun true; Enabled true; Hidden false; ExecutionTimeLimit PT45M; one Exec action with Command, Arguments and WorkingDirectory. |
| D-03 | The arguments are `-X utf8 "ENTRY" run --config "CONFIG"` (UTF-8 mode because the Windows default encoding is not UTF-8, research Pitfall 8), with `--dry-run` and, only with it, `--allow-placeholder` when asked (the smoke task of plan 03-07). Paths with spaces are safe because the entry script and config are double-quoted and the Command is double-quoted when it contains a space (UNVERIFIED until runbook step 6). The arguments carry only paths, never a credential (D-01 of plan 03-01 puts every setting in the config file). |
| D-04 | The renderer refuses what it cannot quote or what is unsafe: relative paths, paths that do not exist (unless check_exists is False, used only by tests), values containing a double quote, a newline, an angle bracket or a percent sign (the scheduler might expand it, UNVERIFIED), values containing `://`, and `--allow-placeholder` without `--dry-run`. `&` is allowed and XML-escaped. The result has no `@@` left and is written as UTF-8 without a byte-order mark; an existing output file is not overwritten without --force. |
| D-05 | The default start boundary is the next time the local clock reads :15 (minute configurable 0 to 59), strictly after now. |
| D-06 | The default interpreter of the renderer is `sys.executable`, the one that ran it, so the validated interpreter is the scheduled one. |
