<objective>
Turn the study into four independent studies on four fresh copies of the same case, each scaled to its own city's targets before its rating is written and its load flow solved, with result rows that stay unique and attributable per city in the existing tables.

Purpose: CD-1 (one network, one case copy per city, four independent load flows) and SCL-02, SCL-03 and SCL-05. Today one case holds all four cities' ratings and one load flow serves them all. This plan keeps today's first-failure behaviour (the first failing city stops the run, as now); plan 04-04 changes it to "attempt all four, fail once naming each city" (CD-8).
Output: the per-city `make_study` in `backend/psse_job/study.py`, `contingency.screen(base, id_prefix="")`, the new test file `backend/tests/psse_scaling_test.py`, recomputed count pins in five test files and the regenerated golden call surface.

Honest scope: the fake proves call order, isolation between copies and failure handling. Whether real PSS/E reads the scaling slots as `SCALE_LAYOUT` says, and whether reloading undoes a scaling, is plan 04-06's laptop check.
</objective>

## Design decisions (planner-locked)

| ID | Decision |
|----|----------|
| PD-1 | `CaseIndex = collections.namedtuple("CaseIndex", ["api", "label", "case_path", "psse_version", "lines", "transformers", "buses", "resolved"])`. `index_case(psspy_module, case_path, mapping)` builds one `PsseApi(psspy_module, protected_path=case_path)`, reads the version, loads the case, reads `branch_table` and `bus_table` (failures are `load_case`, worded as today), runs `check_mapping` (problems are one `mapping` failure, as today) and returns the index. It reads no totals and writes nothing, so a mapping failure still leaves no write call in the fake log |
| PD-2 | `prepare_city_base(index, mapping, selection, city, budget, temp_dir)` in this order: `api.load_case(case_path)` (a failure is `load_case`, "case <label> could not be loaded for <CITY>: <meaning>"); `scale_city_case(api, city, mapping.cities[city].scaling)`; `apply_ratings(api, {city: resolved[city]}, mapping, selection, cities=(city,))`; `solve_base`; the post-solve reads and the collapse guard (moved into a helper `_read_solved_base(api, settings)` that `prepare_base` also uses); `api.save_case(os.path.join(temp_dir, city + ".sav"))` (a failure is `contingency`, as today). It returns a `BaseCase` for that city alone: `cities` holds one CityBase, `area` is `study_area` over `{city: resolved[city]}` with that city's sinks, `temp_dir` is the run's shared directory, `scaling` is the city's Scaling |
| PD-3 | `scale_city_case(api, city, scaling)`: `before = api.read_totals()`; for load then generation, the case's own total must be above 0 ("scaling: <CITY>: the case has no load to scale", or "no generation") and target over own total must lie within `SCALE_FACTOR_BOUNDS` inclusive ("scaling: <CITY>: the load target is outside 0.05 to 20 times the case's own total", the bounds printed from the constant); then `api.scale_case(scaling.load_mw, scaling.gen_mw)`; then `after = api.read_totals()` and each total within `SCALE_TOLERANCE` relative of its target ("scaling: <CITY>: the load total read back differs from the target by more than 0.1 percent", likewise "generation"). Every failure is `StudyFailed("apply_ratings", ...)`; adapter errors become "scaling: <CITY>: <error>" (PsseCallError text names function and ierr only). The read-back is before the solve, because a solve moves the swing machine and voltage-dependent load |
| PD-4 | Module constants in study.py: `SCALE_TOLERANCE = 1e-3`, `SCALE_FACTOR_BOUNDS = (0.05, 20.0)`, `SCALING_METHOD = "scal_2 whole case to the city's target load and generation, load power factor kept, one fresh case copy per city"`. `scaling_record(scaling)` returns `{"basis": scaling.basis, "method": SCALING_METHOD}` |
| PD-5 | `make_study(...).study(selection, context)`: one `Budget`; `index = index_case(...)`; `temp_dir = tempfile.mkdtemp(prefix=_TEMP_PREFIX)` after the index; in a try/finally that calls `_remove_dir(temp_dir)` on every path, for each city in CITIES order: `prepare_city_base`, `contingency.screen(base, id_prefix=city + ":")`, `margin.city_margin(base, city)`, the dispatch row exactly as today (its ValueError is `StudyFailed("dispatch", "<CITY>: <error>")`), then both the dispatch row's and the margin row's `details` get the key `scaling` = `scaling_record(base.scaling)` (copies, never mutating margin's objects). A StudyFailed from any city propagates at once (first-failure, as today; plan 04-04 changes this). After the loop, when the four screens' rows together exceed `run_record.MAX_CONTINGENCY_ROWS` the run fails with `StudyFailed("contingency", "<n> violation rows across the four cities exceed the limit of <cap>; narrow contingency.hops or the scope")`. The result is `contract.StudyResults` with rows through `_with_safe_details`, `n_contingencies` the sum of the four screens' counts, `rate_set` and `psse_version` as today |
| PD-6 | `contingency.screen(base, id_prefix="")`: `contingency_id = id_prefix + outage.key`; `skip_key=outage.key` (the raw key, research Pitfall 2); `_call_failure` keeps the raw key; the default keeps every existing contingency test valid |
| PD-7 | `BaseCase` gains a last field `scaling`; `prepare_base` passes None and otherwise behaves exactly as today (the four cities in one unscaled case). Its docstring says it is kept for the component tests of the screen and the margin (`psse_contingency_test.py`, `psse_margin_test.py`, `psse_study_test.py`) and that the job runs `make_study`'s per-city copies. `apply_ratings(api, resolved, mapping, selection, cities=None)` loops over `constants.CITIES` when `cities` is None, else over the given cities in CITIES order |
