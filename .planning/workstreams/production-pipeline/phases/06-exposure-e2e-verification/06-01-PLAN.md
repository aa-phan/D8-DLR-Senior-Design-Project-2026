<objective>
Expose the ratings read-only, as the phase's tracer: Phase 4's `public.city_rating` -> a
`security_invoker` view `public.latest_rating` (one current row per city) -> SELECT-only grants and an
RLS read policy for the anon role -> a stdlib REST check that reads it the way consumers will.

Purpose: API-01 (consumer tables/views exposed through Supabase REST, read-only for anon under RLS,
`latest_rating` returns one current row per city) and OD-6 (anon reads both the view and the full
table, with writes revoked explicitly, not only blocked by RLS). Proving the role, grant and RLS
behaviour on a local Postgres first catches a privilege mistake before anything touches the shared
project; the live apply and live REST run are 06-02 Task 2.
Output: one migration, one verification SQL file, a local-Postgres harness, a stdlib REST helper,
the read-check script, and offline tests. Nothing is applied to Supabase and nothing is pushed.
</objective>
