<objective>
Lead Phase 2 with one tracer that puts a real cleaning step between `historical_archive.read_history`
and the forecast/detector in `city_pipeline`, marks every row it touches, and stops a rerun from
writing a second row for a slot. The slice is end to end: `dlr_orchestrator.run_dlr_pipeline` ->
`city_pipeline.run_city_pipeline` -> `data_cleaning.clean_history` -> forecast/detector ->
`city_rating.rate_city` -> `historical_archive.append_observation`.

The tracer ships three rules (unparseable timestamp, duplicate instant, fallback row) plus the
marker columns and report shape that plans 02-03 and 02-04 extend. The fallback-row filter that
`city_pipeline` holds today moves into `data_cleaning` unchanged in meaning.

Purpose: SC1 (cleaning sits between read and consume), SC3 (no second row on append, orchestrator
path included), SC4 (cleaned rows carry a marker). Downstream phases assume this API: Phase 3
validates through it, Phase 4 swaps the CSV read for Postgres and passes the same frame shape.
Output: `backend/data_cleaning.py` (new), changes to `backend/city_pipeline.py` and
`backend/historical_archive.py`, `backend/tests/cleaning_pipeline_test.py` and
`backend/tests/data_cleaning_test.py` (new).

Design decided here (all reversible, so no checkpoint): cleaning is a read-time view. It never
writes and never changes a cell, so the archive (and later Postgres) only ever holds rows as
written and the marker lives on the cleaned frame. A persisted marker column was rejected because
`ARCHIVE_COLUMNS` is imported by `forecast_training.city_training_frame` (which indexes a frame by
it) and through that by the shadow collection. On append, the first write for a slot wins.
</objective>
