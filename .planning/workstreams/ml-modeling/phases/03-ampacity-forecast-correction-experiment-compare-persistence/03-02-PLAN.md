<objective>
Land the three small, self-contained building blocks every later plan in this phase depends on, each proven
behavior-preserving before anything is built on it: a pure wind u/v decomposition that provably agrees with
this repo's own wind convention, an additive extraction of the IEEE 738 convective heat-loss term with a
substitution keyword, and an additive extraction of the weakest-link corridor reduction.

Purpose: D-03 permits exactly two additive refactors to existing runtime files, each gated by an equality test
against pre-refactor output. Those gates are the whole reason the refactors are allowed at all, and both are
one-unit-in-the-last-place fragile in ways that look like physics bugs rather than code-motion bugs. Landing
them here, in isolation, with golden-array gates, means every arm scored later in the phase is standing on
physics that is provably identical to the physics the rest of the system uses. The wind decomposition is
grouped into this plan because it shares the same property: it is pure, stateless, and its correctness is
established by agreement with an existing function rather than by inspection.

Output: `backend/wind_vector.py`, an additive `convective_heat_loss` / `natural_convection` / `q_conv_override`
in `backend/thermal_model.py`, an additive `corridor_weakest_link` in `backend/forecast_training.py`, two
golden-reference fixtures, and three test files extended or created.

**Why the sign convention is dangerous enough to need a test rather than a comment.** A 180-degree-flipped
wind still produces a plausible-looking ampacity, because `perpendicular_wind` folds the wind-to-line angle to
an acute angle before projecting. A sign error in the decomposition therefore survives every smoke test and
every eyeball check, and would silently corrupt the wind-correction arm in Plan 03-04. The only honest proof is
a round-trip equality assertion against `perpendicular_wind` itself across the full direction circle.

**Why the convective extraction is dangerous enough to need a golden array.** `ieee738_ampacity` does not call
the module-level air-property helpers — it recomputes the dynamic viscosity inline with the terms grouped
differently. The helper divides by a denominator built as the absolute temperature plus 110.4; the inline code
divides by the film temperature plus 110.4 plus 273.15. Those are algebraically equal and not bit-equal.
An extraction that "tidies" the arithmetic, or that helpfully calls the existing helper, will fail the gate by
roughly one unit in the last place and will read as a physics error rather than as the code-motion error it is.
This plan defends against that with verbatim line movement, a golden array captured before the edit, and exact
array equality.
</objective>
