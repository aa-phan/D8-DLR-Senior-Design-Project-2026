<objective>
Build the two ML correction families and the arm-5 horizon seam as standalone, independently
testable units — deliberately decoupled from the experiment harness so this plan can run in parallel
with Plan 03-04 without contending for `forecast_experiment.py`.

Three things land here, and each one is a place where a plausible-looking shortcut produces a
silently wrong number:

1. **Arm 3, the wind correction**, learned in u/v vector space. Fitting a correction on a direction
   in degrees is the failure `wind_vector.py` was written to prevent, and the reason it is a silent
   failure is documented in that module: `perpendicular_wind` folds the wind-to-line angle to an
   acute angle before projecting, so a wrong direction still produces a plausible ampacity and
   survives every eyeball check.
2. **Arm 4, the cooling correction**, targeting the convective heat-loss term directly and applied
   through the `q_conv_override` seam Plan 03-02 added and proved to be a bit-exact no-op when
   unused. Correcting the physics term rather than the final ampacity is what makes this arm
   distinct from arm 3 rather than a reparameterization of it.
3. **Arm 5's 24-hour target**, which has no clean path today: `build_training_matrix` reads the
   horizon from a module-level global and shifts the target by one row at this project's cadence.
   Pointing it at a 24-hour frame unchanged would produce a one-hour-target model scored as a
   24-hour one — and RESEARCH Pitfall 4 names the exact tell, an arm-5 score suspiciously close to
   the legacy 1-hour arm's magnitude.

Output: `backend/forecast_correction_models.py`, an additive `horizon_minutes` parameter on
`build_training_matrix` gated by a golden capture, and a validation-set selector resolving the two
open parameterization questions with evidence rather than assertion.

**Two open questions are answered here, on the validation set, not up front.** `03-CONTEXT.md`
leaves arm 4's target (predict the convective level, or a scale-free log-ratio against the
forecast's own term) and arm 3's pooling (one pooled per-corridor model with an endpoint indicator,
or one model per city) explicitly undecided, with the instruction to "decide on the validation set."
This plan implements both options in each pair and selects by measurement. The losing option is not
deleted — it stays in the registry with its measured score, so the decision record can state what
was tried rather than only what won.

**Why the reference model refits from scratch (D-02 approach 5).** The shipped per-corridor artifact
was trained on years that overlap this experiment's test range. Loading it would put test-range
observations into the training history of a model being scored on held-out test rows — leakage that
would flatter arm 5 and invalidate the comparison. The refit uses train-plus-validation rows only,
and this plan never touches the production model directory.

**File-ownership boundary.** Plan 03-04 owns `forecast_experiment.py` in this same wave. This plan
must not touch it, must not touch `config.py` (Plan 03-03 landed every constant it reads), and must
not touch `ACKNOWLEDGEMENTS.md` (Plan 03-07 makes one consolidated entry). Wiring these models into
the harness is Plan 03-06's job, in the following wave.
</objective>
