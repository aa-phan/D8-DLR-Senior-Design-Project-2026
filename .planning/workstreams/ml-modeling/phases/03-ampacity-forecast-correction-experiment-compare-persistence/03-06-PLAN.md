<objective>
Commit what this phase expects to find, prove no arm can see its own future, and then score all
seven arms on held-out test rows exactly once.

Purpose: everything before this plan was reversible. A validation score can be re-run after a tweak
without costing anything; a held-out test score cannot. Once a test number has been seen, no
Expectation written afterwards means anything, and every subsequent "small adjustment" is a
selection decision made with the answer visible. This plan is therefore ordered so that the
irreversible step happens last and only after two guards are in place: the Expectation is on disk
and committed, and a leakage suite has demonstrated — by measurement, not by reading the code — that
no arm's prediction moves when its own future is replaced with a sentinel.

Phase 1 found both trained candidates lost to naive persistence at a 60-minute horizon, and that
result is why this phase exists. At 24 hours the incumbent is, if anything, harder to beat: 24 hours
is exactly one diurnal cycle, so persistence here is the day-ago-same-hour baseline that time-series
practice treats as strong rather than weak. D-02 commits this phase to reporting plainly if nothing
beats it. That is a legitimate and useful outcome, and the paired confidence intervals in this plan
are what make the difference between "nothing beat persistence" and "nothing beat persistence by an
amount distinguishable from noise" — two different sentences, only one of which the data may
support.

Output: the Expectation section committed ahead of any test read, a leakage probe suite, all seven
arms wired and scored once on both corridors' held-out test rows with paired bootstrap confidence
intervals, and a transcript for Plan 03-07 to write the verdict from.

**Why the Expectation comes first, mechanically (ROADMAP Success Criterion 5).** Plan 03-03
installed a module-level test-split lock that raises with a message naming this plan. Unlocking it
is a one-line change and it happens in the SAME commit that lands the Expectation — so the git
history itself records that the expectation predates the measurement, and a reviewer can check that
claim with a log command rather than trusting a document's own date field.

**Why the leakage suite measures rather than inspects (ROADMAP Success Criterion 3).** The criterion
asks for proof "not just by construction." Reading the feature lists and concluding they look clean
is construction. Replacing every truth column with a sentinel, re-running every arm, and asserting
that only the oracle's output changes is measurement — and it catches the cases a reading would
miss, such as a column silently carried through a merge suffix or a frame accidentally passed where
its filtered sibling was intended.
</objective>
