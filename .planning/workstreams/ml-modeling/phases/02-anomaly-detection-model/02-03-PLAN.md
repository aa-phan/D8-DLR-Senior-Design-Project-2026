<objective>
Discharge ANOM-01's fourth named per-variable baseline — load — with a real, executed, training-time-only characterization against historical ERCOT settlement load, and prove by test that it never reaches the live `check()` path.

Purpose: ANOM-01 names "wind, temp, solar, load" as the per-variable baselines the trained model is built on. D-02 resolved the load half to training-time-only, because `raw_data` does not carry load at inference time and wiring it in is Track 1's scope. That resolution is only honest if the load half is actually *done* at training time and the boundary is actually *enforced* — a deferred item with no evidence and no guard would be the requirement quietly dropped. This plan executes the characterization, writes its evidence, and installs the test that keeps load out of the runtime path.

Output: an additive extension to `backend/ercot_data_retriever.py` (returns its frame, accepts an explicit zone selection, loops per calendar year), `characterize_load` plus a `--characterize-load` entry point in `backend/anomaly_training.py`, the per-corridor zone mapping in config, `data/models/anomaly_load_characterization.json`, and the D-02 boundary test.

**Scope resolution (Claude's Discretion in CONTEXT.md).** CONTEXT.md leaves open whether the load characterization is "a lightweight sanity check or a more thorough correlation analysis." This plan scopes it as a correlation-and-coverage sanity check: per corridor, the retrieved load window and row count, the matched zone columns, and the Pearson correlation between the zone load series and each of the three weather variables the model is fitted on, joined on `datetime_utc`. That is enough to state in Plan 02-04's record whether the weather envelope the model learned looks sane against known load-driven demand patterns, without building a second modelling effort inside a validation step.
</objective>

<flagged_assumptions>
- **A-09 (correlation is the chosen depth).** CONTEXT.md leaves the load characterization's depth to discretion. This plan chooses coverage plus Pearson correlation against each fitted variable, not a modelling effort. Risk if wrong: a linear correlation can be near zero while a real non-linear relationship exists, so a weak number here is weak evidence of *linear* association only — Plan 02-04's record must say exactly that rather than reading a low correlation as "load is irrelevant".
- **A-10 (city averaging is presentation-only).** The pooled observation frame carries two cities per timestamp, so the correlation summary averages them to get one row per timestamp to join against a single regional load series. This averaging exists only inside `characterize_load` and never touches the fitted feature matrix, which uses each city's own unaveraged reading per D-01. Stated here because an averaged series is a different statistical object from the one the model learned.
- **A-11 (zone substrings are a regional proxy, not a corridor measurement).** ERCOT weather zones are much larger than a transmission corridor; `SOUTH` and `WEST` are the closest available proxies for the two corridors, not measurements of load on those specific lines. To be stated in Plan 02-04's Limitations.
</flagged_assumptions>
