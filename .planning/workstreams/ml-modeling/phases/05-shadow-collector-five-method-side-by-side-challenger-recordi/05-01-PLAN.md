<objective>
Get a human's explicit sign-off on the one irreversible decision this phase makes before any task
implements it: the new nested-per-candidate JSONL record shape that replaces today's flat,
single-candidate schema.

Purpose: `forecast_shadow_pipeline.py:906-932`'s `log_prediction` writes one flat JSON object per
line -- `method`, `ampacity_amps`, `fallback_used`, `fallback_reason`, `model_version`,
`input_provenance` all top-level, one candidate per line. D-06 requires every one of those fields
per candidate, independently, for five candidates every cycle -- which is not a field you can add to
the existing shape, it is a restructuring of the shape itself. `shadow-collection-data` already
carries real, already-collected entries in the OLD flat shape (confirmed live by commit history:
`c09c53d`, `30d69e6`, `4e73935`, `417dc54`, `b38c2b5` are all real collection/infra commits on that
data lineage). Those old rows cannot be rewritten in place without violating the append-only,
never-overwrite discipline this project fixed a real data-loss bug to establish (`417dc54`) --
so whatever shape is approved here has to coexist with the old shape forever, not replace it
retroactively. That is what makes this decision one-way: once new-shape rows start accruing next to
old-shape rows in the same `.jsonl` files, every future reader of that file (this phase's own
`forecast_shadow_render_table.py`, any later analysis script, whoever eventually mines this data for
the Nov 24 evaluation's observational context) has to handle both shapes forever. Changing the shape
again later means a SECOND coexisting-shapes problem stacked on this one.

This plan is deliberately only a checkpoint -- no implementation -- per this project's planning rule
that a blocking checkpoint and its implementing code never share a plan. 05-02 depends on this plan
and implements exactly what gets approved here.

Output: an explicit, recorded human decision on the new shape and the historical-data strategy,
captured in this plan's own SUMMARY so 05-02 can cite it.
</objective>

D-06 requires every one of `ShadowPipeline.log_prediction`'s existing fields (`method`,
`ampacity_amps`, `fallback_used`, `fallback_reason`, `model_version`, `input_provenance`), plus a
new `status`/`reason` pair (D-04/D-07), independently per candidate, for five candidates every
cycle. That is not an additive field on the existing flat shape -- it is a restructuring of the
record itself. `shadow-collection-data` already carries real rows in the OLD flat shape, and this
project's own append-only discipline (the data-loss bug fixed in commit `417dc54`) means those rows
can never be rewritten in place -- so whatever is approved here coexists with the old shape
forever. Nothing in 05-02 through 05-05 can proceed correctly until this is settled, and getting it
wrong is expensive to unwind once new-shape rows start accruing next to old ones.

**Recommended shape**, one JSON object per corridor per cycle:
```
{
  "schema_version": 2, "corridor": "...",
  "initialization_time": "...", "availability_time": "...",
  "decision_time": "...", "valid_time": "...", "horizon_minutes": 1440,
  "logged_at": "...", "basis_caveat": "(unchanged string, same as today)",
  "candidates": {
    "ml_wind_corrected":      { "status": "ok|unavailable|failed", "ampacity_amps": "float|null",
                                 "fallback_used": "bool", "fallback_reason": "string|null",
                                 "model_version": "string|null", "input_provenance": "dict|null",
                                 "reason": "string|null" },
    "ml_cooling_corrected":   "...same seven keys...",
    "raw_forecast":           "...same seven keys...",
    "persistence_24h":        "...same seven keys...",
    "reference_ml_refit_24h": "...same seven keys..."
  },
  "method": "ml_wind_corrected",
  "ampacity_amps": "candidates.ml_wind_corrected.ampacity_amps, verbatim",
  "fallback_used": "candidates.ml_wind_corrected.fallback_used, verbatim",
  "fallback_reason": "candidates.ml_wind_corrected.fallback_reason, verbatim",
  "model_version": "candidates.ml_wind_corrected.model_version, verbatim",
  "input_provenance": "candidates.ml_wind_corrected.input_provenance, verbatim"
}
```
The six top-level mirror fields are an EXACT, byte-for-byte copy of
`candidates["ml_wind_corrected"]`'s own fields -- including when `ml_wind_corrected` itself is
`"unavailable"` or `"failed"` that cycle, in which case `method` stays the literal string
`"ml_wind_corrected"` and `ampacity_amps` is `null`. This is D-01 read literally: a legacy
single-method reader (`forecast_shadow_healthcheck.py`) sees exactly what it saw before -- an
honest null on a bad cycle, never a different candidate's value silently promoted into that slot.
Confirmed directly: `forecast_shadow_healthcheck.py` lines 44-77 reads only `entry.get('fallback_used')`
and `entry['logged_at']` at the top level, so this mirror requires zero code change there.

**Recommended historical-data strategy:** leave every already-committed flat-shape row exactly as
it is -- no migration, no backfill, no rewrite, following directly from the append-only discipline
commit `417dc54` established. A reader (05-05 Task 1's `forecast_shadow_render_table.py` update)
distinguishes old rows from new rows per-line via `entry.get("schema_version", 1) >= 2`, rendering
old rows as a single-method row (as today) and new rows with all five candidates.

Also worth confirming: the `candidates` object roughly quintuples each line's byte size (no
operational cost -- git diffs on text, nothing parses this at volume); and the new `reason` field
(D-04/D-07, why NO value exists this cycle) is deliberately kept distinct from the existing
`fallback_reason` field (D-06, a method-internal fallback that still produced a genuine value).
