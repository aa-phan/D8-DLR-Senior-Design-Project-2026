<objective>
Prove the five-candidate architecture end to end, for one corridor, one live cycle: one shared
fetch, five candidates attempted with per-candidate validation and failure isolation, the new
nested schema approved in 05-01, and a genuinely new `persistence_24h` implementation that reads
its own anchor correctly.

Purpose: 05-RESEARCH.md's own finding is that today's collector has no per-candidate concept at
all -- `collect_once` calls `forecast_shadow_demo.run_once(corridor, "ml_wind_corrected")` once per
corridor, one hardcoded method-name literal, full stop (`forecast_shadow_collect.py:101`). Three of
the five candidates' prediction math already exists and works (`CorridorWindCorrectionMethod`,
`CoolingCorrectionShadowMethod`, `RawForecastShadowMethod`), but a closer read than 05-RESEARCH.md's
own architecture diagram shows two things that diagram did not call out: `CoolingCorrectionShadowMethod`
and `RawForecastShadowMethod` are single-city predictors today -- nothing corridor-reduces them the
way `CorridorWindCorrectionMethod` already corridor-reduces wind correction -- and
`CoolingCorrectionShadowMethod.predict` needs `anchor_air_temp`/`fcst_perp_wind_ms`/
`anchor_perp_wind_ms` columns that the live anchor fetch (`fetch_live_anchor_observation`) does not
populate today. D-06's "per-city predictions and the corridor-level weakest-link minimum... for all
five candidates" is not optional breadth here -- it is a real gap this plan closes for the first
time, for three candidates, not just one.

`persistence_24h` and `reference_ml_refit_24h` have no live implementation of any kind. This plan
builds `persistence_24h` for real (the only one of the two that is pure wiring, no new offline
artifact needed) and wires `reference_ml_refit_24h` as an honest stub -- `status="unavailable"` with
a reason naming the missing persisted model -- because that artifact genuinely does not exist yet
(05-RESEARCH.md: `data/shadow/models/` holds only `ml_wind_corrected_*.joblib` and
`ml_cooling_corrected_*.joblib`). D-04 is explicit that this is the correct behavior for a missing
artifact, not a blocker; 05-04 fits and commits the real artifact and wires the real prediction path
later in this phase, in parallel with 05-03.

Output: the five-candidate orchestration, the new schema, `persistence_24h` for real, and one live
cycle for one corridor proving all five are attempted and recorded honestly.

**Why `persistence_24h` reads the prior entry's `raw_forecast` value, not `ml_wind_corrected`'s.**
D-05 says read "from the shadow collector's own prior logged entry... or an equivalent
decision-time-available source," leaving the exact field to this plan (05-CONTEXT.md's own
Claude's-Discretion note). `raw_forecast` is the least-processed of the five candidates -- the
forecast's own weather run through IEEE 738 with no correction model's own output folded in.
Anchoring persistence on `ml_wind_corrected`'s (or `ml_cooling_corrected`'s) own prior prediction
would make one baseline arm secretly derivative of a correction model's output, which blurs
exactly the model-independent reference line every other arm in Phase 3/4's own comparison was
measured against. If the matching prior entry's `raw_forecast` candidate was itself unavailable or
failed, `persistence_24h` propagates that as its own unavailable reason rather than silently
falling through to a different candidate's value.
</objective>
