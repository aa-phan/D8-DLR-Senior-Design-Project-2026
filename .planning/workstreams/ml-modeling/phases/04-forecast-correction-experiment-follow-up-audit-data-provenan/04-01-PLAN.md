<objective>
Build the spine the whole audit hangs on, and prove it end to end on one real finding.

Purpose: this phase's central risk is not that a statistic is computed wrongly — it is that the
audit quietly takes a second look at Phase 3's frozen held-out test rows, or that it reads the
decision record, agrees with it, and calls that an audit. Both failures are cheap to commit and
expensive to discover later. So the first thing built is not a statistic: it is (a) a mechanical
guard that raises if any audit computation is handed a frozen-test-window row, (b) three explicitly
named data bases so that every later claim in this phase can say which basis it rests on, and (c)
one genuine, code-grounded finding carried all the way from a file read to a cited sentence in a new
decision record — so the path from "read the code" to "published claim" is proven before five more
findings are poured through it.

The finding chosen for that proof is the one 04-RESEARCH.md confirmed is a real gap and is checkable
with zero network access: the entire "truth" side of Phase 3's experiment is itself a physics-model
output (IEEE 738 run over ERA5/ERA5-Land reanalysis weather), not a sensor measurement — and the
frozen record's Data-provenance and Limitations sections never say so. That is not a nitpick. Every
ampere in the frozen record's Verdict is an agreement between two model outputs, and a reader who
does not know that will read those margins as field-validated accuracy.

Output: `backend/forecast_experiment_audit.py` with the guard, the three bases, an independent
re-derivation of the frozen split boundary and a basis manifest; a network-free test file; a new
audit record with all ten section headings and its first real finding written in with file:line
citations; and a human checkpoint surfacing how much real data actually exists before any later plan
writes a claim from it.

**Why the boundary is re-derived rather than trusted (D-01).** The frozen record states its test
split starts 2026-03-17. The harness computes that boundary from the assembled frame's own min and
max timestamps — so the boundary is a function of the window END, which defaults to "yesterday".
Re-running the harness today therefore produces a *different* test-split start than Phase 3's run
did. That has two consequences this task must surface: the frozen record's own numbers are only
reproducible with the window end pinned, and this phase must pin the frozen window's dates as
explicit audit constants rather than recomputing them and drifting off the frozen boundary. Both
belong in the audit's findings, not in a footnote.

**Why the row-count checkpoint exists.** 04-RESEARCH.md's central finding is that Phase 3 persisted
no per-row predictions and no fitted models — so every new statistic in this phase has to be computed
from data assembled fresh. Its second finding is that a genuinely fresh, post-frozen-window period
may contain zero usable rows today. Both facts change what this phase can honestly claim. A human
should see the measured row counts before any plan starts writing sentences that depend on them.
</objective>

**1. `backend/forecast_experiment_audit.py`** — a standalone, offline, additive audit module.

Open with a module docstring in the same register as the harness's own: state plainly that this
module is standalone, is never imported by the runtime pipeline, imports `config`,
`experiment_splits`, `forecast_experiment` and `forecast_training` for reuse, and adds only new
symbols — it never edits, monkeypatches, or shadows anything in the modules it imports. State in the
docstring that it deliberately reaches for a handful of the harness's underscore-prefixed helpers,
and why: duplicating the harness's assembly or scoring logic in a second module would create exactly
the drift an audit exists to detect, so reuse of a private helper is the lesser of the two evils, and
the alternative is named so a future reader does not "fix" it by copying code.

Define the frozen-window pins as module constants sourced from the frozen decision record, each with
a comment naming the section of that record it came from:
  - `FROZEN_WINDOW_START` — the assembled window start (`2024-01-20`).
  - `FROZEN_TEST_SPLIT_START` — the frozen held-out test split's first date (`2026-03-17`).
  - `FROZEN_WINDOW_END` — the frozen window's last date (`2026-09-29`).
The comment on `FROZEN_TEST_SPLIT_START` must state why this is a pinned constant and not a
recomputation: the harness derives the boundary from the assembled frame's own span, so the boundary
moves as the window end advances, and recomputing it today would place the audit's guard on a
different date than the rows Phase 3 actually scored.

Define `AUDIT_BASES` as a mapping from each of the three basis names to a short description of what
a claim resting on that basis may and may not say:
  - `SYNTHETIC` — generated in process; validates that a computation is correct; supports no claim
    about this project's real corridors.
  - `ABLATION` — real rows strictly before `FROZEN_TEST_SPLIT_START`; supports replication,
    relative-ordering and ablation findings; is NOT a confirmation basis, because that calendar range
    was read during Phase 3's own development.
  - `FRESH` — real rows strictly after `FROZEN_WINDOW_END`; the only basis on which this phase may
    make a confirmation claim; may legitimately contain zero rows.

Implement `assert_basis_excludes_frozen_test_rows(frame, *, basis)`. Validate `basis` against
`AUDIT_BASES` first, raising a `ValueError` that lists the three valid names. For `SYNTHETIC`,
require that the frame carry no real-corridor marker and return immediately. For `ABLATION`, every
`datetime_utc` must be strictly before `FROZEN_TEST_SPLIT_START`. For `FRESH`, every `datetime_utc`
must be strictly after the end of the `FROZEN_WINDOW_END` day. On violation, raise a `ValueError`
that names the basis, the offending row count, the first three offending timestamps, and the frozen
window's two pinned dates — following `assert_exact_lead`'s own convention of putting every number a
reader needs into the message body. Return a summary dict with the basis name, the row count, and the
first and last timestamp (or explicit nulls for an empty frame). An empty frame returns the summary;
it does not raise.

Implement `rederive_frozen_split_boundaries(frame)`: delegate to the harness's own boundary
computation (do not reimplement the fraction arithmetic) and return both the resulting
`SplitBoundaries` and a comparison dict recording the re-derived `test_start` date, the pinned
`FROZEN_TEST_SPLIT_START`, whether they match, and the frame's own min and max timestamps — so a
mismatch is diagnosable from the returned value alone without re-running anything.

Implement `truth_provenance_finding(frozen_record_path=...)`. It returns a structured finding with:

model output with no sensor-measured validation, computed by scanning those two sections for a small
set of disclosure markers rather than hard-coded; and the finding's severity and its one-sentence
consequence for a reader. Keep every cited line number in a named constant or the returned dict —
never buried in prose — so a later plan can re-assert the citations mechanically.

Every stochastic routine anywhere in this module reuses
`config.FORECAST_EXPERIMENT_CORRECTION_RANDOM_STATE`. Do not add a second seed constant.

Never invoke the harness's own per-corridor runner, its single-city tracer runner, or its
command-line entry point — all three are named in this task's `<read_first>`. Those are the only
functions that carry the split-name argument capable of requesting the frozen rows; the audit
