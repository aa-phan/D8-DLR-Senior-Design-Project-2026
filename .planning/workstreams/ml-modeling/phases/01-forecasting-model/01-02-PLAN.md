<objective>
Turn Plan 01's single-estimator tracer into D-01's evidence-based choice: fit and score both a regression candidate and a neural-network candidate on the identical real assembled matrix, score `naive` and `ewm` on the identical series through the existing `backtest_residuals`, pick the winner on measured held-out MAE, and do it independently for each of the two corridors.

Purpose: D-01 is explicit that regression-vs-neural-network is decided on measured out-of-sample accuracy with **no default lean**. That is only honest if both arms are actually fitted and both arms' numbers survive into the record — which means the bake-off machinery, the four-row comparison report, and the MAE-driven selection rule all have to exist before Plan 03 can write anything truthful about what was chosen and why.

Output: `bakeoff_corridor` / `baseline_scores` / `select_winner` in `backend/forecast_training.py`, two new `config.py` tunables, a machine-readable per-corridor report, per-corridor persisted winners for both corridors, and the offline tests that keep the selection rule honest.
</objective>

**1. `backend/config.py` — two new tunables**, appended to the predictive-layer block with the same decision-citing comment style:

Comment why a small fold count rather than per-row retraining: an estimator's training step at every row of a multi-year hourly series is the documented cost trap (`01-RESEARCH.md` Pitfall 1), while a handful of expanding folds preserves the same train-strictly-precedes-test guarantee.

**2. `backend/forecast_training.py` — the bake-off.**
- `CANDIDATE_ESTIMATORS` — an ordered mapping of candidate name to a zero-argument factory returning a fresh unfitted estimator. Exactly two entries, one per arm of D-01's question: a regression candidate built from `sklearn.ensemble.HistGradientBoostingRegressor` with a fixed `random_state`, and a neural-network candidate built from `sklearn.neural_network.MLPRegressor` with `hidden_layer_sizes=(32, 16)`, `max_iter=2000`, a fixed `random_state`, and `early_stopping=False`. Name the entries descriptively (e.g. by estimator class) so the report and the validation record both read unambiguously. A factory rather than a shared instance, because each fold must fit a fresh estimator.
  - `MLPRegressor` is scale-sensitive in a way the tree candidate is not, and the raw features span amps in the thousands, degrees Celsius, and unit-interval sine/cosine terms. Wrap the neural-network candidate in `sklearn.pipeline.make_pipeline(StandardScaler(), MLPRegressor(...))` so the comparison measures the architecture rather than a missing scaling step — otherwise the neural-network arm loses for a reason that has nothing to do with D-01's question.
- `bakeoff_corridor(X, y) -> dict` — build `TimeSeriesSplit(n_splits=config.FORECAST_ML_BAKEOFF_SPLITS)` over `X`. For each candidate, for each fold: build a fresh estimator from the factory, train it on the fold's train rows, predict the fold's test rows, and accumulate the absolute and squared errors. Report each candidate's pooled MAE and RMSE across all folds plus the total number of held-out rows scored. Use `TimeSeriesSplit` as the only fold source — do not hand-roll positional slicing (`01-RESEARCH.md` "Don't Hand-Roll").
- `baseline_scores(frame) -> dict` — score `naive` and `ewm` on the SAME assembled corridor frame by calling `ampacity_forecast.backtest_residuals(series, method, min_train_rows=config.FORECAST_MIN_HISTORY_ROWS, halflife_min=config.FORECAST_EWM_HALFLIFE_MIN)` and reducing the returned residual array to MAE and RMSE. This is the apples-to-apples requirement in ROADMAP SC3/SC4: the baselines must come from the module's own walk-forward function, not from a second error computation written here. Record the residual count as that candidate's held-out row count.
- `corridor_report(corridor, frame, X, y) -> dict` — merge `bakeoff_corridor` and `baseline_scores` into one mapping with a `candidates` sub-mapping holding all four entries, plus `corridor`, `rows` (the assembled frame's row count), `window_start` and `window_end` (the frame's first and last `datetime_utc`, as ISO strings), `feature_columns` (a copy of `ampacity_forecast.ML_FEATURE_COLUMNS`), and `horizon_min`. The window fields exist so a shortened run is visible in the evidence rather than hidden behind a score (this plan's first prohibition).
- `select_winner(report) -> str` — over the two `CANDIDATE_ESTIMATORS` names only, return the one with the lowest `mae`. Raise `ValueError` naming the problem when a candidate entry is missing from the report or its `mae` is not a finite number — a winner chosen despite a missing measurement is exactly the default lean D-01 forbids. On an exact tie, break it deterministically by `rmse`, then by `CANDIDATE_ESTIMATORS` order, and state which tiebreak fired in the report.
- Refactor `fit_corridor_model(X, y, estimator)` to take an unfitted estimator and return it fitted, so the same function serves the tracer's single fit and the winner's full-window refit. Keep any existing call site working.
- Extend `main(argv=None)` with a `--bakeoff` flag. With the flag: assemble each requested corridor's frame, build its matrix, produce `corridor_report`, choose the winner via `select_winner`, refit that winner once on the full matrix, persist it via `persist_corridor_model`, and write the accumulated per-corridor reports as JSON to `os.path.join(config.FORECAST_ML_MODEL_DIR, config.FORECAST_ML_BAKEOFF_REPORT_NAME)`. Also print a human-readable four-row comparison table per corridor to stdout (candidate, MAE, RMSE, rows), and print the chosen winner. Without the flag, behavior is exactly Plan 01's.
