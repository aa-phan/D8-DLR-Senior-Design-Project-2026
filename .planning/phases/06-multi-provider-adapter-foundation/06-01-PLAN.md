<objective>
Establish per-field provenance as a first-class part of the pipeline data contract: extend
`PIPELINE_SCHEMA` to v3 with four categorical provenance columns, teach `validate_pipeline_row`
to validate a categorical (string-valued) column without crashing on its existing numeric range
path, and prove the whole thing end-to-end by having `fetch_weather`'s existing station path
emit provenance-tagged rows that validate cleanly.

Purpose: this is the one-way half of Phase 6 (D-03). `PIPELINE_SCHEMA`'s additive-only rule means
that once these four columns exist and downstream consumers read them, collapsing or renaming them
is a breaking schema change, not an addition. Landing the schema shape correctly — and proving it
against a real `fetch_weather` call — before any dispatch or merge work is what makes Phases 7-10
cheap.

Output: `PIPELINE_SCHEMA_VERSION = 3`; four `required: False` categorical columns; a
`KNOWN_PROVIDER_NAMES` registry; `weather_provider.attach_provenance`; a new
`backend/tests/weather_provider_test.py`; a v2→v3 regression block appended to
`backend/tests/units_def_test.py`.
</objective>

  <decision>
Two things get locked here, both one-way once written:

**(a) The four column names.** D-03 locks `wind_source`, `temp_source`, `humidity_source`,
`solar_source` — one per weather-field family, rather than the two (`wind_source`, `solar_source`)
literally named as examples in `data_provider.md`. Confirm these exact four spellings.

**(b) How a string-valued column lives inside a numeric schema.** CONTEXT.md did not specify this;
RESEARCH.md Open Question #1 flagged it. `validate_pipeline_row` currently does
`lo, hi = spec["range"]` then `float(np.mean(value))` on every present column — a string crashes it.
The three candidate shapes:

| Option | Shape | Pro | Con |
|---|---|---|---|
| **A (recommended)** | Categorical entries carry `"unit": "categorical"`, `"range": None`, `"allowed_values": KNOWN_PROVIDER_NAMES`; `validate_pipeline_row` branches on `spec.get("unit") == "categorical"` and checks membership | Self-documenting; catches a typo'd provider name (`"synotpic"`) at validation time; branch keys off the *schema*, so a numeric value wrongly written into a provenance column is reported, not crashed on | Adds one new optional field name (`allowed_values`) to the schema vocabulary |
| B | Keep the entries numeric-shaped; `validate_pipeline_row` skips any column whose runtime value `isinstance(value, str)` | Smallest diff | A typo'd provider name passes silently; a numeric value written into a provenance column still crashes on `lo, hi = None` |
| C | Do not add provenance to `PIPELINE_SCHEMA` at all; carry it as untyped DataFrame columns | Zero schema risk | Fails WX-07 and ROADMAP SC3 outright — the requirement is explicitly a schema extension |

**Recommendation: Option A**, plus seeding `KNOWN_PROVIDER_NAMES` with all five names this
milestone will use — `"synoptic"`, `"tceq"`, `"asos"`, `"nsrdb"`, `"open_meteo"` — so Phases 7-10
register a provider by using its name, with no schema change (D-04's stated intent).
  </decision>
