# C4 — Weather Ingestion

**Phase:** 2 (Core Consolidation), extended in Phase 7 (Trivial-Integration Providers), Phase 8 (NSRDB Solar Integration), and Phase 9 (TCEQ CAMS Integration) · **Effort:** M · **Status:** Implemented — provider-agnostic adapter (`backend/weather_provider.py`) now carries five real providers behind it: Synoptic (station primary), ASOS 1-minute (station supplement), TCEQ CAMS (station primary, second station-path provider), Open-Meteo (grid backfill), and NSRDB (grid solar).

**Responsibility:** Discover weather stations near target corridors and fetch time-series observations (temp, wind speed/direction, solar, humidity) for them, behind an interface that doesn't hardcode which provider is behind it — because the provider decision is explicitly unresolved (see `PRD.md` §7.1).

## Current Implementation

- `backend/station_explorer.py::get_network_id(token, shortname) -> str`, `get_all_stations(token, network_id=None) -> pd.DataFrame`, `haversine_km`, `rank_by_corridor` — Synoptic station discovery and corridor-proximity ranking.
- `backend/dlr_pipeline.py::get_wtm_stations(bbox=None) -> pd.DataFrame` — a second, overlapping station-metadata fetch (bbox-based rather than corridor-proximity-based).
- `backend/dlr_pipeline.py::fetch_timeseries(stids, start, end) -> pd.DataFrame` — 5-minute observations via Synoptic `/stations/timeseries`, long-form indexed by `(stid, datetime_utc)`, now also carrying null-tolerant `lat`/`lon` columns parsed from each station's `LATITUDE`/`LONGITUDE` (Phase 6). Requires `SYNOPTIC_TOKEN` env var (`backend/dlr_pipeline.py::_token()`).
- `backend/dlr_pipeline.py::profile_missing_data(df)` — logs per-station, per-variable missing-data percentages and flags fully-dead sensors.

## Interface & Data Contract

Output rows conform to the weather-observation subset of `PIPELINE_SCHEMA` (C2): `air_temp` (degC), `wind_speed` (m/s), `wind_direction` (deg), `solar_radiation` (W/m²), `relative_humidity` (%), indexed by `(stid, datetime_utc)`.

**Implemented:** `backend/weather_provider.py::fetch_weather(location, start, end, provider="synoptic") -> pd.DataFrame`. `location` is type-dispatched (Phase 6): a `list[str]` of station IDs selects the station path, a `(lat, lon)` tuple of two numbers selects the grid path, and every other shape raises `ValueError` naming the received type/length rather than being silently misread. The station path delegates to `dlr_pipeline.fetch_timeseries` and tags each returned row with per-field provenance via `attach_provenance` (`PIPELINE_SCHEMA` v3's four categorical `*_source` columns — `wind_source`, `temp_source`, `humidity_source`, `solar_source` — naming the provider that actually supplied that field family, never inferred or defaulted). `merge_observations(station_frame, grid_frame) -> pd.DataFrame` is the city-keyed combination seam (D-05): it keys both sides on `(city, datetime_utc)` (via `resolve_station_city`/`attach_city`, never a default or nearest-guess fallback) and combines them with pandas' `combine_first` — station values win where both sides supply a field, and each field's provenance travels with its value. `dlr_pipeline.py` gained only additive `lat`/`lon` columns for this purpose (see Known Issues — the duplicate station-metadata fetchers inside it are still there).

**Phase 7 additions (WX-02, WX-04):** the station path (`provider="synoptic"`) is now transparently supplemented with ASOS 1-minute wind/temp observations via `weather_provider._supplement_with_asos`, which calls `asos_provider.fetch_asos_1min` per resolved city using `config.ASOS_STATIONS` (the IEM ASOS network's 3-letter FAA station codes — `AUS`/`CRP`/`MAF`/`ELP`, not the 4-letter ICAO codes used elsewhere in the project) and unions the result into the Synoptic series via the existing `merge_observations` (reused unmodified — no new merge function was needed). No caller of `fetch_weather` changed: the supplement is automatic, and a station-path result stays keyed on `(stid, datetime_utc)` exactly as before unless ASOS actually supplied rows for the call, in which case it re-keys to `(city, datetime_utc)` with `stid` demoted to a nullable column. A well-formed, zero-row ASOS response (a real 1-minute-sensor outage) is non-fatal; a malformed body, an unknown-station response, or an HTTP error raises. The grid path (`_fetch_grid`) now has its first real implementation: `provider="open_meteo"` calls `open_meteo_provider.fetch_open_meteo`, which issues exactly one request against Open-Meteo's Archive API and returns the full temp/wind/solar/RH variable set for a single `(lat, lon)` point — no merge is performed on this path, since it stands alone as a historical-backfill source for C9/C10 training data (D-04) rather than a supplement to a primary. Both `asos_provider.py` and `open_meteo_provider.py` are unauthenticated: neither reads an environment variable, imports `os`, or references a token/key/secret, and neither introduced a new `.env` entry (ROADMAP Success Criterion 4).

**Phase 8 additions (WX-03):** the grid path now has a second real implementation, `provider="nsrdb"`, calling `nsrdb_provider.fetch_nsrdb(lat, lon, start, end)`. It supplies `solar_radiation` only, because NREL's own documentation says the response's 2m MERRA-2 reanalysis wind must not be used for wind power calculations, so NSRDB rows deliberately carry no wind, temperature or humidity column and their corresponding provenance columns (`wind_source`, `temp_source`, `humidity_source`) stay null (D-02) while `solar_source` reads `nsrdb`. It requires two environment values, `NREL_API_KEY` and `NREL_API_EMAIL`, read only from the environment with the same env-var-or-raise shape as `dlr_pipeline._token()`, and raises `EnvironmentError` — deliberately a different exception type from the `ValueError` this module raises for an untrusted response, so a future fallback implementation can distinguish a misconfigured machine from a failing provider. The endpoint is year-scoped (it has no start/end parameter at all), so a window spanning calendar years is issued as one request per year and reassembled into one ordered, de-duplicated frame, unlike every other provider in this codebase. Data coverage begins in 2018 (`NSRDB_FIRST_COVERED_YEAR`) and an earlier year is rejected locally before any network call, while a later year is left to the endpoint's own rejection. The developer host is `developer.nlr.gov` following the National Laboratory of the Rockies rename — the hostname cited in `data_provider.md` no longer resolves and will be corrected when Phase 10 ratifies that document.

**Phase 9 additions (WX-01):** the station path gains a second real implementation, `provider="tceq"`, delegating to `tceq_provider.fetch_tceq` for one CAMS site's wind/temperature/relative-humidity observations, tagged `"tceq"` via the same `attach_provenance` mechanism the Synoptic branch uses. Unlike Synoptic, no ASOS supplement is applied on this branch — `_supplement_with_asos` is Synoptic-specific and mixing it into the TCEQ branch was not in WX-01's scope. `tceq_provider.fetch_tceq` is the milestone's highest-effort integration because it is an HTML report scrape of TCEQ's public `daily_summary.pl` CGI endpoint via `bs4.BeautifulSoup`, not a REST or JSON client: the endpoint answers HTTP 200 with a generic site-selection form for an unknown or unreachable CAMS ID, so response validation requires both a site-specific `<h1>` link and a data `<table>`, and every request must carry `select_date=user` because the CGI otherwise silently answers with today's report at HTTP 200 for any requested date. Per-city CAMS site IDs live in `config.TCEQ_STATIONS` (Austin CAMS 38, Corpus Christi CAMS 83, Midland CAMS 1095, El Paso CAMS 41), chosen on wind/temperature/relative-humidity completeness alone. Because `daily_summary.pl` reports exactly one calendar day per request, `fetch_tceq` decomposes any multi-day window into one request per LOCAL calendar day and reassembles the result (concatenated, sorted, de-duplicated, restricted back to the caller's window), capped at `TCEQ_MAX_DAYS_PER_FETCH` (31) days — a caller needing a longer historical backfill is pointed at Open-Meteo (WX-04) instead of looping this provider hundreds of times against a free, unauthenticated, public government endpoint. Timestamps are built from a fixed per-site integer UTC offset (`TCEQ_FIXED_UTC_OFFSET_HOURS`), never a DST-aware `zoneinfo`/`pytz` lookup, because TCEQ publishes every report in fixed Local Standard Time year-round: Austin, Corpus Christi, and Midland are always CST (`-6`) and El Paso is always MST (`-7`), regardless of the calendar date. Austin and Midland do not monitor Relative Humidity at all, so a fetch for either site returns a present but entirely-null `relative_humidity` column with a null `humidity_source`, while `wind_source` and `temp_source` still read `"tceq"` for those same rows. The failure scope is raise-only, with no fallback: an unreachable endpoint, a malformed or wrong-site report, an absent Wind Speed/Wind Direction/Outdoor Temperature row, a truncated row, a window selecting zero rows, an out-of-range converted value, or a `weather_provider._fetch_station` call naming more than one CAMS ID under `provider="tceq"` each raise a named `ValueError` rather than returning a partial or fabricated frame — fallback to Synoptic for this station path is explicitly deferred to WX-06 / Phase 10, which can wrap this raise behavior without needing to change it.

## Known Issues

- `backend/station_explorer.py` and `backend/dlr_pipeline.py` each implement their own station-metadata fetch (`get_all_stations` vs. `get_wtm_stations`) with different filtering (corridor-proximity vs. bounding box) and different output columns (`elev_ft` vs. `elevation_m`) — duplicated logic that should consolidate into one.
- `network_id = 152` is hardcoded in `backend/station_explorer.py:99`, with the shortname-lookup path (`get_network_id`) commented out — brittle if the network ID changes. **Still open** — explicitly out of scope for this pass per the Open Questions below.
- ~~Output file/log-message mismatch...~~ **Fixed** — `station_explorer.py`'s log line now correctly reports `data/wtm_stations_austin.csv`.
- Missing `solar_radiation` is filled with a hardcoded `1000` W/m² (`backend/dlr_pipeline.py:348`) rather than being flagged — happens to be conservative for ampacity (more assumed solar → lower computed rating) but is an undocumented magic number, not a named constant. **Still open** — `dlr_pipeline.py` was deliberately not touched this pass (see Interface & Data Contract above), to keep C4 and C5's concurrent work non-overlapping.
- Debug `print()` calls inside `fetch_timeseries` (`backend/dlr_pipeline.py:138-143`) alongside the module's proper `logging` calls elsewhere. **Still open**, same reason.
- No retry/backoff or rate-limit handling on the Synoptic requests — relevant given the free-tier constraints noted in `PRD.md` §7.1. **Still open.**
- **Still duplicated**: `backend/station_explorer.py::get_all_stations` and `backend/dlr_pipeline.py::get_wtm_stations` remain two separate station-metadata fetchers — consolidating them was explicitly out of scope (see Open Questions).
- **Newly found via live verification (2026-08-25)**: `data/wtm_stations_austin.csv` — the file `config.DEFAULT_STATION_SOURCE` points at, i.e. the pipeline's own default station list — contains only 2 real stations (`MOFWL`, `MOLOK`), and **both return zero observation rows** under the currently-configured Synoptic token. Station *metadata* access works for both (they show up in `/stations/metadata`), but the `/stations/latest` endpoint returns `RESPONSE_CODE: 2, "No stations found... or your account does not have access"` for them — a real account/tier restriction, not a code bug. This means `dlr_pipeline.py`'s `__main__` block, run as-is today with default config, would silently produce an empty result. A different station (`KAUS`, Austin-Bergstrom Airport) confirmed full data access and was used for all the live verification below. Worth fixing the default station source before anyone relies on `python backend/dlr_pipeline.py` producing real output.
- **Newly found**: stations that lack Synoptic's `solar_radiation` field entirely (confirmed true for both `KAUS` and the two `wtm_stations_austin.csv` stations) mean the `dlr_pipeline.py:348` hardcoded `1000` W/m² fallback (see above) isn't an edge case — it's the *normal* path for airport/METAR-style stations. This raises the priority of turning it into a named, documented constant.
